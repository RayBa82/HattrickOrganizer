## Testing supporter-only output

Appending `overrideIsSupporter=X` to a request makes that single call behave as Off (`-1`),
Silver (`0`), Gold (`1`), Platinum (`2`) or Diamond (`3`). It does not work for `teamdetails`.
Useful to check what a non-supporter gets from supporter-gated paths such as `placeBid` or the
tracking types 5/8/9/10 of `currentbids`.

## challenges (version 1.6)

`actionType` is one of `view` (default), `challengeable`, `challenge`, `accept`, `decline`,
`withdraw`; all but `view` need the `manage_challenges` scope. Optional on every action: `teamId`
(defaults to the primary senior team) and `isWeekendFriendly`.

- `challengeable` - `suggestedTeamIds`, comma-separated: checks whether each team can be
  challenged. Used by the `check_challengeable` MCP tool.
- `challenge` - `opponentTeamId` (required), `matchType` 0 normal / 1 cup rules, `matchPlace`
  0 home / 1 away / 2 neutral, `neutralArenaId` (required when `matchPlace=2`).
- `accept` / `decline` / `withdraw` - `trainingMatchId`.

There is **no** CHPP action for Hattrick's friendly pool, in `challenges` or any other file. The
docs index also states that CHPP products may only use the documented interfaces, so joining
the pool stays a manual step on the website.

## transfersearch — input parameters (version 1.1)

Taken from the rendered CHPP docs page, saved under
`docs/raw/Transfer Search » CHPP Files help » CHPP » Community » Hattrick_files/transfersearch.html`.

| Parameter        | Req. | Type             | Default       | Notes |
|------------------|------|------------------|---------------|-------|
| `file`           | yes  | `transfersearch` |               | |
| `version`        | no   | `1.1` / `1.0`    | 1.0           | |
| `ageMin`         | yes  | unsigned int     |               | minimum age in years |
| `ageDaysMin`     | no   | unsigned int     | 0             | |
| `ageMax`         | yes  | unsigned int     |               | maximum age in years |
| `ageDaysMax`     | no   | unsigned int     | 111           | |
| `skillType1`     | yes  | SkillID          |               | main skill |
| `minSkillValue1` | yes  | SkillLevel       |               | |
| `maxSkillValue1` | yes  | SkillLevel       |               | |
| `skillType2..4`  | no   | SkillID          | not specified | further skills |
| `minSkillValue2..4` | no | SkillLevel      | not specified | |
| `maxSkillValue2..4` | no | SkillLevel      | not specified | |
| `specialty`      | no   | SpecialtyID      | not specified | |
| `nativeCountryId`| no   | unsigned int     | not specified | country of birth |
| `tsiMin`         | no   | unsigned int     | not specified | |
| `tsiMax`         | no   | unsigned int     | not specified | |
| `priceMin`       | no   | Money            | not specified | |
| `priceMax`       | no   | Money            | not specified | |
| `pageSize`       | no   | unsigned int     | 25            | max 100 |
| `pageIndex`      | no   | unsigned int     | 0             | zero based |

Server-side rules, per skill pair: the window may span at most 4 levels **counted inclusively**, so
max and min may differ by at most **3** — the docs say "up to 4 levels", but `minSkillValue1=7&maxSkillValue1=11`
is answered with error 10, "No primary skill with min and max range has been specified", while
`7..10` works; set pieces, leadership
and experience need a minimum level of 5, keeper a minimum of 3. `SkillID`: 1 keeper, 2 stamina,
3 set pieces, 4 defending, 5 scoring, 6 winger, 7 passing, 8 playmaking, 9 trainer (not searchable),
10 leadership, 11 experience.

The age window is limited too, and the limit depends on `ageMin`: up to `ageMin=18` only
`ageMax - ageMin <= 1` is accepted, from `ageMin=19` a width of 2 works. Wider windows at higher ages
are untested. A violation is answered with error 10, `Additional Info: ageMin` — which names the
parameter but not the actual rule. `pageSize` and `pageIndex` are documented as optional but must
always be sent.

Documented example: `?file=transfersearch&version=1.1&ageMin=20&ageMax=22&skillType1=8&minSkillValue1=7&maxSkillValue1=9`

The file description states it is *not* meant to be polled by bots, only fetched on manual user
request.

## playerdetails (version 3.0)

Requested by `Connector.downloadPlayerDetails`. Answers for **any** player, including a foreign one
on a non-supporter account (`UserSupporterTier: none`), and carries `OwningTeam/TeamID`. This is the
only CHPP file that can be asked about one named player's market status: `transfersearch` has no
`playerId` parameter, and `currentbids` is read-and-delete only (`view` / `ignoreTransfer`, no
add-to-hotlist action).

Four things about it that cost a live fetch to learn:

- **`<TransferDetails />` is present-but-empty when the player is not listed.**
  `getElementsByTagName("TransferDetails").item(0)` returns a non-null `Element` for an unlisted
  player, so a presence check reports everybody as listed. The detection signal is
  `<TransferListed>`, a clean `True`/`False`. `<BidderTeam />` is the same trap one level down when
  there are no bids.
- **`<PlayerSkills>` is pruned, not withheld.** It is present in both responses. An unlisted player's
  contains exactly one child, `<StaminaSkill>` — so stamina is public always and the other seven are
  published only while he is on the market. Since `XMLManager.xmlIntValue` defaults a missing child
  to `0`, parsing the block unconditionally reports seven real skills as zero.
- **`Salary` carries the abroad surcharge.** A player with `<IsAbroad>True</IsAbroad>` reports a
  salary exactly 1.2× the base wage that `transfersearch` reports for the same player. Both files
  report SEK; the ×10 between SEK and a EUR display is a separate currency-rate concern.
- The listed shape is:

  ```xml
  <TransferListed>True</TransferListed>
  <TransferDetails>
    <AskingPrice>2850000</AskingPrice>
    <Deadline>2026-09-05 20:08:31</Deadline>
    <HighestBid>0</HighestBid>
    <BidderTeam />
  </TransferDetails>
  ```

`XMLPlayersParser.parseMarketPlayerFromString` handles all of the above.
`parsePlayerDetailsFromString` is a wrapper over it that returns `null` for a foreign player.
`XMLPlayersParser.createPlayerDetails` reads the same `TransferDetails` block a third time, into the
HRF hash; it is safe only by accident, because `xmlValue` returns `""` for a missing child rather
than throwing.

## CHPP write actionTypes used by HO


HO issues these write actions on behalf of the managed team (exposed over MCP, see
`docs/superpowers/specs/2026-09-02-chpp-write-operations-over-mcp-design.md`):

| file | version | actionType | purpose |
|---|---|---|---|
| `training` | 2.2 | `setTraining` | set senior training type / intensity (0-100) / stamina share (5-100); `teamId` required, needs the `set_training` scope |
| `matchorders` | 3.0 | `setmatchorder` | upload the match order for an upcoming game (pre-existing); carries positions, `kickers` (always 11 slots, id 0 where empty) and `substitutions`. **Needs Supporter**, although the CHPP matchorders docs do not say so: without it Hattrick answers CHPP error 6, "setmatchorder is only available for Hattrick Supporters". A refused order can also come back as `OrdersSet="False"` with a `Reason` instead of an error code |
| `challenges` | 1.6 | `view` / `challengeable` / `challenge` / `accept` / `decline` / `withdraw` | list and manage friendly challenges; `view` and `challengeable` are reads |
| `playerdetails` | 3.2 | `placeBid` | place a transfer bid (`bidAmount` / `maxBidAmount` are Money in SEK; needs the `place_bid` scope and Supporter) |
